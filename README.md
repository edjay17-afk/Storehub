## Workflow

1. The app seeds 1,361 products from `data/Products.csv` once. Existing Product Id values are preserved; blank SKUs and repeated names are allowed for imported products.
2. Record a delivery in **Warehouse receiving**, or add a new product with its initial warehouse quantity. Stock is always received into TheDailyCentro Warehouse. A warehouse count sets an absolute quantity and records the reason.
3. Use **Product requests** to create a supplier purchase order addressed to the warehouse, or a warehouse-to-branch transfer. Creation does not change stock.
4. Receive purchase orders partially or fully; quantities enter warehouse stock. Ship transfers to deduct warehouse stock, then confirm branch receipt to add branch stock. Shipments cannot exceed available warehouse stock. Repeated shipping/receiving is rejected. Created documents can be cancelled before stock has moved. Shipped transfers and partial purchases require reconciliation rather than cancellation.
5. Download CSVs from **Orders & transfers**, or export changed products / the full catalog from **Products**.

## CSV compatibility and reconciliation

Products exports reproduce 39 active columns (the original template minus the three 688 columns), the instruction row, quoted fields, and CRLF line endings. New products require a unique SKU and export a blank Product Id so StoreHub can assign it. Existing Product Id values are never rewritten. New products support Simple inventory and Fixed pricing; imported products keep their existing metadata.

Stock transfers reproduce the supplied 21 columns; purchase orders reproduce the supplied 23 columns, with a summary row followed by item rows. Currency headings remain `Cost (RM)`, `SubTotal (RM)`, `Total (RM)` exactly as supplied. The app uses local IDs (`LOCAL-PO...`, `LOCAL-ST...`), and does not claim these are StoreHub-generated IDs.

The supplied transfer and purchase order files are historical reports. Their matching layout is implemented, but StoreHub's import acceptance, mandatory identifiers, and permitted statuses have **not** been verified. Obtain the actual import templates or perform a small test import before relying on these exports for bulk imports. Products compatibility also requires a StoreHub test import. The API connection described below does not establish CSV import acceptance.

Blank quantities are zero for local arithmetic, matching the product template's documented default; original blank cells remain blank until changed. Existing negative values are preserved. Costs are raw values from the files; the app does not add tax, currency conversion, or discounts. Product quantities and purchase/transfer quantities are in the base unit. Unit conversion is not implemented.

The baseline is the supplied product snapshot, not live stock. Historical transfer and purchase-order rows are kept as reference files and are never replayed into stock. Reconcile current StoreHub stock before importing. A Products CSV includes quantities for all four active locations on each exported row. Importing these absolute quantities and separately applying the same receipts/transfers in StoreHub can double-count movements. Choose one reconciliation method for each stock movement.

Changed product exports include every product changed since initialization; downloading does not clear flags or mark it imported. Products created through this app are linked to their StoreHub Product Id after a successful API response. Products created separately in StoreHub are read during sync; uncertain matches need explicit review.

## StoreHub partner API connection

The StoreHub button (link icon on mobile) opens the connection page. It supports a connection test, manual sync, location mapping, optional 15/30/60-minute scheduled reads, product/stock comparison, recent purchase orders and branch restock suggestions. The app reads the documented partner endpoints only. It excludes store 688 from mapping and inventory calls. The warehouse and three original branches match automatically only when the store names match exactly after normalizing punctuation and spaces.

Credentials are loaded server-side by `start.ps1` and `start-lan.ps1`. To set or replace them on this computer, run `powershell -ExecutionPolicy Bypass -File .\setup-storehub.ps1 -Username YOUR_SUBDOMAIN`, enter the API token in the hidden prompt, and restart the app. `data/storehub-connection.xml` uses Windows DPAPI through PowerShell `Export-Clixml`: only the same Windows account on this computer can decrypt it. This file is ignored by Git and is not served by the app. The token is never returned by browser API responses. No username/token entry form is exposed over LAN HTTP. The credentials supplied during setup are used only for `https://api.storehubhq.com` with HTTP Basic authentication; redirects are refused.

Sync keeps API stock in a separate snapshot. It does not replace quantities imported from your CSV or quantities changed by local receipts, counts or transfers. Remote sales are used for demand estimates; they never replay stock movements. Existing locally changed product details are preserved. API `unitPrice` is not copied into the CSV's `Tax-Inclusive Price` field. The initial live comparison found the CSV prices were 1.12 times the API unit prices across all 1,361 products; the publish form therefore asks for the separate tax-exclusive unit price rather than assuming a conversion for new products. Unknown API products are imported with pending initial balances; after mapping all locations, review and initialize those untouched products explicitly. API-only products lack complete CSV fields (including tax-inclusive prices): their quantity/full-catalog CSV export is blocked rather than risking an incomplete import. Obtain the complete Products CSV from StoreHub for these fields; merging a newer source CSV is not automated by this version.

For new products created locally, select the product in the connection page, enter the tax-exclusive price and preview its details. **Create in StoreHub** sends `POST /products` only after you confirm the preview. Initial warehouse quantities are not sent. SKU/barcode collisions block creation and allow a reviewed link to an existing synced product. A timeout or unknown creation result blocks retries until you sync and reconcile/link it, preventing duplicate product creation. Product publishing was validated with simulated API responses; no test product was created in the live account.

Restock suggestions target seven days of average net sales over the last 30 days for each product and branch, rounded up. Current StoreHub quantity reduces the shortage. Ideal and warning stock do not override this sales-based target. Cancelled sales are excluded; returns reduce demand. Outstanding local transfers reduce branch demand and reserve warehouse availability. Warehouse availability is the conservative minimum of local and remote stock after reservations; it is allocated across branch suggestions without counting the same balance twice. **Draft request** fills a local transfer for review; it does not submit an order or change stock. Suggestions are estimates based on snapshots and need review before saving a request. Recent StoreHub purchase orders are read-only and are not received into the local ledger.

The supplied partner API has no documented stock-adjustment, transfer-creation or purchase-order-creation endpoints. Those operations retain the existing CSV workflow. Do not invent inventory adjustments using sales/return transactions. CSV purchase-order/transfer import acceptance still needs verification in StoreHub; matching the supplied export layout does not establish that StoreHub accepts it as an import.

Requests are serialized and spaced at least 0.6 seconds apart. Sync commits its core catalog/inventory snapshot only after all those reads succeed; failures keep the previous snapshot. Optional sales/purchase-order failures show a warning and keep previous cached records. Date ranges are subdivided when the documented 5,000-record cap is reached; a capped daily result fails visibly. Scheduled reads default to manual and run only while the app is running. An automatic sync failure switches scheduling back to manual to avoid repeated rate-limit or permission errors. This throttle coordinates this app, not other StoreHub integrations on the same account.

Integration checks: `C:\Python314\python.exe -m pytest tests -q`. They cover local balance preservation, removed-store filtering, snapshot rollback, initial-balance review, explicit tax-exclusive pricing, duplicate prevention, uncertain-write recovery, transfer reservations, returns and request-origin checks. A database backup was saved at `data/warehouse-before-storehub.db` before the first live sync.
